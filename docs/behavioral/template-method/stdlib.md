# 15.3 Go 里的模板方法

## 嵌入不是继承

从 Java 转过来，很容易想用嵌入模拟「父类定流程、子类覆盖步骤」：

```go
--8<-- "codes/behavioral/templatemethod/trap.go:trap"
```

`Run` 的接收者 `b` 是 `baseExporter` 类型，Go 在编译时就确定了它调用的是 `baseExporter.Header`。嵌入只是把方法「提升」到外层，**不会让内层方法回头调用外层的方法**。

所以 Go 里的写法是：流程写成接收接口的函数（如 `Export(e Exporter, ...)`），步骤通过接口调用，调用的才是实际类型的方法。

## 标准库中的模板方法

| 位置 | 固定的流程 | 你提供的步骤 |
|---|---|---|
| `sort.Sort(data)` | 排序算法 | `sort.Interface`：`Len`、`Less`、`Swap` |
| `heap.Push` / `heap.Pop`（`container/heap`） | 堆的上浮、下沉 | `heap.Interface`：比较、交换、追加、弹出 |
| `fs.WalkDir(fsys, root, fn)` | 递归遍历目录 | 回调 `fn`：每个文件做什么 |

`sort.Sort` 是最经典的一个：排序的每一步怎么比较、怎么交换由你决定，但先比较谁、再交换谁，由 `sort` 包决定。

## 模板方法与策略

两者都是「把会变的部分交出去」，区别在交出去多少：

| | 模板方法（本章） | 策略（[第 13 章](../strategy/index.md)） |
|---|---|---|
| 替换什么 | 流程中的**某几步** | **整个**算法 |
| 流程归谁 | 模板函数，调用方改不了 | 每个策略自己决定 |
| 典型例子 | `sort.Sort` 的三个方法 | `slices.SortFunc` 传入的比较函数 |

## 什么时候用

<div class="grid" markdown>

!!! success "适合"

    - 多个功能流程相同，只有个别步骤不同
    - 流程有严格顺序，不希望每个实现自己乱排
    - 想在一处统一修改流程（加日志、加检查）

!!! failure "不适合"

    - 每种实现的流程本身就不同，硬抽骨架只会更绕
    - 只有一种实现，没必要拆步骤
    - 步骤太多、接口太大，实现一个格式要写一堆空方法

</div>
